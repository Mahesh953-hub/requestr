# (A) Executive summary — how the reference products work end-to-end

## A.1 Reqable (the current market leader; successor to HTTP Canary)

Reqable is a **hybrid Flutter UI + C++ core engine** application. DeepWiki's architecture analysis of `reqable/reqable-app` states the C++ core owns "the MITM proxy functionality, protocol processing (HTTP/1.x, HTTP/2, HTTP/3, WebSocket), SSL/TLS operations including certificate management, and high-speed data processing" while Flutter renders the UI — this mirrors the older HTTP Canary architecture where a Java core (NetBare) sat under a plain Android UI ([deepwiki.com/reqable/reqable-app/2-architecture](https://deepwiki.com/reqable/reqable-app/2-architecture), [github.com/reqable/reqable-app](https://github.com/reqable/reqable-app)).

**Capture path (documented in the official docs):**
1. **Desktop:** the app configures the *system proxy* (HTTP/HTTPS/SOCKS4/SOCKS4a/SOCKS5; port 9000 by default, protocol auto-detected from the first bytes of the client connection) — [reqable.com/en-US/docs/capture/proxy](https://reqable.com/en-US/docs/capture/proxy).
2. **Mobile (iOS/Android):** the app establishes a **local VPN tunnel** (`VpnService` on Android) instead of a system proxy, because apps ignore system proxies — explicit statement in the introduction: "On desktop platforms, it intercepts traffic through the system proxy; on mobile platforms, it intercepts traffic through a VPN tunnel" — [reqable.com/en-US/docs/introduction](https://reqable.com/en-US/docs/introduction/).
3. Inside the VPN, Reqable runs the classic **MITM** model: the tunneled streams are terminated by an in-process proxy server; the client-facing TLS leg is terminated with a per-host leaf certificate signed by the Reqable CA; a second TLS leg goes upstream. The official FAQ exposes the internal plumbing: "Record Mode" = VPN vs proxy, and **"Enhanced Mode"** where "the proxy protocol uses `socks5` instead of `http`" between the tunnel and the local proxy — i.e., the mobile transport is `VpnService tun → tun2socks-style bridge → local SOCKS5/HTTP proxy → MITM engine` ([reqable.com/en-US/docs/faq/android](https://reqable.com/en-US/docs/faq/android), [reqable.com/en-US/docs/changelogs/android](https://reqable.com/en-US/docs/changelogs/android/)).
4. The core parsing pipeline is inherited from **NetBare**, the open-sourced library that powered HTTP Canary. Reqable's own traffic-list column documentation says so verbatim: in the `Origin` column, "since Reqable uses the `Netbare` library as the MITM core, the source of the captured traffic will be displayed as `Netbare`" ([reqable.com/en-US/docs/capture/column](https://reqable.com/en-US/docs/capture/column)). This is the single most important product/architecture fact in this dossier: **the Reqable family is a direct, still-evolving descendant of the NetBare interception architecture**, which is open source ([github.com/MegatronKing/NetBare-Android](https://github.com/MegatronKing/NetBare-Android)).

**Protocol support (as of the current docs):**
- *API Debugging (capture):* HTTP/1.x and HTTP/2; **HTTP/3 (QUIC) explicitly "not yet supported"** in capture; TLSv1.1/1.2/1.3; HTTP/HTTPS/SOCKS4/4a/5 proxy dialects; WebSocket (upgraded from HTTP/1.1); SSE; IPv4+IPv6 — [reqable.com/en-US/docs/introduction](https://reqable.com/en-US/docs/introduction/).
- *API Testing (client):* HTTP/1.1, HTTP/2, **HTTP/3 (QUIC) as a sending client** with automatic downgrade to HTTP/1.1 when the server lacks support — [reqable.com/en-US/docs/rest/protocol](https://reqable.com/en-US/docs/rest/protocol).

**How Reqable deals with HTTP/3 in capture (the pragmatic industry answer):** it **does not MITM QUIC on-device**. Instead the changelog shows a deliberate strategy: "SOCKS5 UDP proxy automatically blocks HTTP3/QUIC requests" — by dropping UDP/443 in the tunnel (or not forwarding it through the SOCKS5 UDP gateway), QUIC clients fall back to HTTP/2 over TCP, which the MITM engine can decrypt. The Android FAQ/GA and changelogs never claim QUIC decode in capture ([reqable.com/en-US/docs/changelogs/android](https://reqable.com/en-US/docs/changelogs/android/), [reqable.com/en-US/docs/introduction](https://reqable.com/en-US/docs/introduction/)).

**Feature surface (desktop = full debugging, mobile = observation-only):** the introduction has a *caution* box: "To prevent abuse, the Reqable mobile app does not provide debugging-related features such as rewrite, breakpoint, and script." The mobile app keeps: capture (VPN mode), traffic list, per-app filtering ("Applications support bypass mode", v2.25.1), SSL proxying rules, inspectors, compose/repeat, HAR/cURL export, Report Server upload, and collaboration with the desktop app ([reqable.com/en-US/docs/introduction](https://reqable.com/en-US/docs/introduction/), [reqable.com/en-US/docs/changelogs/android](https://reqable.com/en-US/docs/changelogs/android/), [reqable.com/en-US/docs/capture/report-server](https://reqable.com/en-US/docs/capture/report-server)). This mobile/desktop split is a product-policy decision (abuse prevention + Play review pressure), not a technical ceiling — relevant to requestr's product choices.

**SSL interception mechanics (docs):** a per-user CA; automatic decrypt when the CA is installed; undecrypted flows shown with a lock icon; **SSL Proxying rules** (Intercept All / Bypass All / per-domain wildcard rules, with "Hide bypassed traffic"); **custom client/server certificates per domain** for mutual-TLS and certificate-pinning scenarios (import crt/pem/der/p12/pfx/zip). The presence of *custom-server-certificate-per-domain* is the documented answer to pinning on the server side: you hand Reqable the app's actual expected cert and it presents it during the client leg ([reqable.com/en-US/docs/capture/ssl](https://reqable.com/en-US/docs/capture/ssl)).

**CA trust on Android (FAQ):** Chrome's trust policy has flipped over versions — the FAQ states newer Chrome builds ignore a CA installed in the *system* certificate directory and require the **user** certificate directory, while older builds required the system directory ("If you are not sure which method to choose, you can try both"). Firefox on Android uses its **own CA store** and needs the hidden setting *Secret Settings → Enable "Use third party CA certificates"* ([reqable.com/en-US/docs/faq/android](https://reqable.com/en-US/docs/faq/android)).

**Captured traffic UX:** a dense, column-configurable list (ID, method, host, path/URL, status, protocol-as-ALPN-name, duration, stream ID, connection ID, origin, interceptor badges, device, application/package, remote+local IP:port, request/response timestamps, sizes, arbitrary header columns), per-row status dot (green=complete / yellow=failed / gray=in-progress), multi-session tabs, explorer sidebar filters (bookmark / device / application / domain, OR-combined), quick filters (protocol, content-type, status range) and a 3-condition search, plus "turbo mode" that stops updating the list for throughput ([reqable.com/en-US/docs/capture/list](https://reqable.com/en-US/docs/capture/list), [reqable.com/en-US/docs/capture/column](https://reqable.com/en-US/docs/capture/column), [reqable.com/en-US/docs/capture/search](https://reqable.com/en-US/docs/capture/search), [reqable.com/en-US/docs/capture/turbo](https://reqable.com/en-US/docs/capture/turbo)).

**Debugging tools (desktop; the same taxonomy requestr should implement as a rule engine):** Gateway (L4/L7 allow-only/bypass/block/suspend on domain+IP/CIDR+HTTP+WebSocket rules), Mirror (host mapping at proxy layer with Host/SNI/CN strategies), Rewrite (redirection, replace request, replace response, modify request, modify response; Content-Length auto-recalculation; regex with capture groups; priority redirection > replacement > modification), Breakpoint (URL-wildcard rules, one thread per paused request, bounded thread pool), Python Script (onRequest/onResponse lifecycle, request interruption by returning None, cross-process `shared` state), Network Throttling presets (offline/bad/slow/fast/2G/3G/4G/5G/wi-fi with bandwidth/latency/loss tables), multi-session recording, HAR import/export, Charles `.chls` import via Charles CLI conversion ([reqable.com/en-US/docs/capture/gateway](https://reqable.com/en-US/docs/capture/gateway), [reqable.com/en-US/docs/capture/mirror](https://reqable.com/en-US/docs/capture/mirror), [reqable.com/en-US/docs/capture/rewrite](https://reqable.com/en-US/docs/capture/rewrite), [reqable.com/en-US/docs/capture/breakpoint](https://reqable.com/en-US/docs/capture/breakpoint), [reqable.com/en-US/docs/capture/script](https://reqable.com/en-US/docs/capture/script), [reqable.com/en-US/docs/capture/network-condition](https://reqable.com/en-US/docs/capture/network-condition), [reqable.com/en-US/docs/capture/charles](https://reqable.com/en-US/docs/capture/charles)).

**Replay:** repeat one or more selected flows; advanced repeat with iterations/delay/interval/proxy-choice; **up to 255 concurrent connections, excess queued** — the documented concurrency ceiling is a concrete performance target for requestr's replay path ([reqable.com/en-US/docs/capture/repeat](https://reqable.com/en-US/docs/capture/repeat)).

**Data export / reporting:** HAR open+export; a "Report Server" that POSTs each completed session as HAR-shaped JSON to a user server with gzip/brotli/zstd compression and no retries; code snippets in ~20 languages/libraries (C, Go, Java×4, JS×4, Kotlin, Node×4, PHP×2, Python×2, Shell) — i.e., a curlconverter-class generator ([reqable.com/en-US/docs/capture/har](https://reqable.com/en-US/docs/capture/har), [reqable.com/en-US/docs/capture/report-server](https://reqable.com/en-US/docs/capture/report-server), [reqable.com/en-US/docs/capture/view](https://reqable.com/en-US/docs/capture/view)).

## A.2 HTTP Canary — the ancestor, and its open architecture (NetBare)

HTTP Canary (com.guoshi.httpcanary) was the original product by the same author; it was renamed to Reqable and its public repo now redirects to Reqable ([github.com/MegatronKing/HttpCanary](https://github.com/MegatronKing/HttpCanary)). But the interception library behind it — **NetBare** ("Net packets capture & injection library designed for Android", GPLv3, ~1.4k GitHub stars) — is fully open source and documents the entire pipeline ([github.com/MegatronKing/NetBare-Android](https://github.com/MegatronKing/NetBare-Android)). Verified from the NetBare source tree and README:

1. **VPN transport:** a `VpnService` subclass creates the tun; config requires `MTU ≥ 2048`, a **local proxy-server IP** (an "A-class" private address, e.g. `10.x.x.x`), and a `0.0.0.0/0` route so all IPv4 packets enter the tun. UID dumping is optional and explicitly documented as battery-draining ("dumpUid ... 耗电方法, 建议false").
2. **TUN → local proxy handoff:** packets from the tun fd are fed to an in-process **TCP proxy server built on Java NIO** (a `ServerSocketChannel` bound to the VPN subnet address, driven by a `Selector`). Every TCP connection gets two channels — `TcpProxyTunnel` (client/VPN side) and `TcpRemoteTunnel` (upstream side) — bound together by `TcpVATunnel`, which routes bytes through the `VirtualGateway`. NetBare hand-parses the **IP and TCP headers in Java** (`ip/IpHeader.java`, `ip/TcpHeader.java`) and reassembles streams; `SessionProvider` keys flows by (local IP:port, remote IP:port) and a `/proc`-based `UidDumper`/`UidProvider` maps flows to app UIDs (`net/UidDumper.java`).
3. **VirtualGateway = interceptor chain** (the conceptual ancestor of requestr's `RuleEnforcer` pipeline): `Interceptor`/`HttpInterceptor` with `intercept(chain, ByteBuffer)` request/response hooks plus `onRequestFinished/onResponseFinished`; built-in interceptors include `SSLCodecInterceptor` (TLS via JSSE), `HttpHeaderSniff/Separate/Parse`, and — notably — a **hand-written HTTP/2 implementation** (`http2/Hpack.java`, `http2/Huffman.java`, `http2/Http2.java`, frames/settings/streams with `Http2DecodeInterceptor`/`Http2EncodeInterceptor`) and an injection framework (static vs dynamic injection).
4. **Certificates:** a self-signed root CA stored as a JKS (`ssl/JKS.java`); per-host leaf certificates generated with **BouncyCastle** `X509v3CertificateBuilder` — CN = hostname, **SAN extension** populated, **random positive serial with a 16-bit reserve**, and **1-day validity** (`ssl/CertificateGenerator.java`). An `SSLWhiteList` controls which hosts get decrypted.
5. **The canonical HTTP Canary user guide** (preserved in mirrors) documents the operational side: since Android 7, apps must opt into user CAs via `networkSecurityConfig`; third-party apps are captured by installing them inside **VirtualApp** (a virtual-app container) plus the CA; apps that validate certificate signatures (pinning) are declared uncapturable "unless we can obtain the server's certificate" ([github.com/99969/HttpCanary/blob/master/app_ug_zh.md](https://github.com/99969/HttpCanary/blob/master/app_ug_zh.md)).

So HTTP Canary's end-to-end flow, verified from source: **app socket → kernel routing → tun fd → Java NIO proxy server on the VPN subnet → VirtualGateway interceptor chain (header sniff → SSL codec → HTTP/1.1 or HTTP/2 parser) → upstream socket**, with per-flow session/UID bookkeeping and injection/replay hooks at the gateway.

## A.3 mitmproxy — the reference for MITM correctness and protocol translation

mitmproxy is the best-documented general MITM engine and defines the correctness bar:

- **Explicit mode:** client sends `CONNECT host:port`, proxy answers `200`, then performs the MITM dance: pause the client TLS handshake just after SNI, open the upstream connection **using the SNI hostname** (upstream certificate sniffing), extract CN **and all SANs** from the real upstream cert, forge a leaf signed by the mitmproxy CA covering that CN+SAN set, and resume the client handshake — including the case of `CONNECT 1.2.3.4:443` where no hostname is given at all ([docs.mitmproxy.org/stable/concepts/how-mitmproxy-works](https://docs.mitmproxy.org/stable/concepts/how-mitmproxy-works/)).
- **Transparent mode:** needs a redirection mechanism (iptables) plus a "host module" that recovers the original destination (SO_ORIGINAL_DST / nftables) and auto-detects TLS by peeking for a ClientHello regardless of port ([docs.mitmproxy.org/stable/concepts/how-mitmproxy-works](https://docs.mitmproxy.org/stable/concepts/how-mitmproxy-works/), [docs.mitmproxy.org/stable/concepts/modes](https://docs.mitmproxy.org/stable/concepts/modes/)).
- **Protocol stacks:** HTTP/1.x on a custom `h11`-based stack; HTTP/2 on `hyper-h2` with **automatic HTTP/2↔HTTP/1.1 translation** when the upstream doesn't speak h2; WebSocket on `wsproto`; DNS on a custom implementation; generic TCP/TLS and UDP/DTLS proxying with opportunistic TLS detection ([docs.mitmproxy.org/stable/concepts/protocols](https://docs.mitmproxy.org/stable/concepts/protocols/)).
- **HTTP/3:** native support since mitmproxy 11, built on **aioquic**, available in reverse-proxy, local and **WireGuard** modes; QUIC v1 only (v2/RFC 9369 unsupported); transparent-mode QUIC is not functional because UDP interception is missing in that mode; regular CONNECT proxying cannot carry QUIC at all (UDP). Caveat from the project: "HTTP/3 support has only been extensively tested with cURL" ([mitmproxy.org/posts/releases/mitmproxy-11](https://www.mitmproxy.org/posts/releases/mitmproxy-11/), [docs.mitmproxy.org/stable/concepts/protocols](https://docs.mitmproxy.org/stable/concepts/protocols/)).
- **Moving to Rust:** the next proxy core is a Sans-I/O design being rewritten in Rust (`mitmproxy_rs`); community Rust rewrites of the interception path report ~1,901 RPS full-HTTPS-MITM vs ~631 RPS for mitmdump 11.0.2 and SSE first-chunk latency 128 ms vs 533 ms (tokio + h2 + http + rustls, deliberately no hyper in the data path) ([github.com/mitmproxy/mitmproxy_rs](https://github.com/mitmproxy/mitmproxy_rs), [mitmproxy.org/posts/new-proxy-core](https://www.mitmproxy.org/posts/new-proxy-core/)).

## A.4 Charles Proxy — the desktop UX and cert model reference

Charles describes itself as a local debugging proxy that works via system/device proxy configuration, with **SSL Proxying** enabled per host; it dynamically generates site certificates signed by the Charles root CA, and its docs are explicit that on Android 7+ real interception is only reliable for **apps you control** (network-security-config must opt in to user CAs), that pinning blocks it, and that "SSL Proxying can only be used with applications you control" on modern Android ([charlesproxy.com/documentation/proxying/ssl-proxying](https://www.charlesproxy.com/documentation/proxying/ssl-proxying/), [charlesproxy.com/documentation/using-charles/ssl-certificates](https://www.charlesproxy.com/documentation/using-charles/ssl-certificates/)). It also popularized the traffic-list + focus/inspector split, breakpoints, rewrite, map-local/map-remote (Reqable's Mirror/Rewrite-redirect equivalents) — the direct UX ancestor of the "capture list + per-flow inspector" pattern every product in this class shares.

## A.5 Architectural invariants distilled from the four references

1. **Transport and MITM are decoupled.** Every product routes traffic into a userspace proxy endpoint first (system proxy on desktop, `VpnService` tun on Android, root iptables where available) and does TLS termination in a separate engine. requestr's current split (Rust bridge → Kotlin `MitmProxyEngine`) matches the industry pattern.
2. **The MITM layer is a rules pipeline, not a linear relay.** NetBare's VirtualGateway, Reqable's interceptor icons on each row, and mitmproxy's addon API are all the same shape: request/response intercept chains that can observe, mutate, block, and substitute.
3. **Header/body correctness invariants are non-negotiable:** Content-Length must be recomputed on any header/body mutation; Host/SNI/CN handling is a first-class policy (Reqable Mirror); upstream CN+SAN cloning is the standard technique for browser-grade leaf certs; serials must be positive and unique per issuer.
4. **HTTP/3 is not actually MITM'd on devices.** Reqable blocks QUIC in the tunnel and forces HTTP/2; mitmproxy supports it only in reverse/local/WireGuard modes with cURL-grade confidence; HTTP Canary never shipped it. Passive QUIC observation (keylog-driven, or QUIC-packet parsing without decryption) is a different, additive capability — which is exactly what requestr's `quic/` module already does.
5. **Mobile products deliberately split the feature set** (capture+inspect+test on-device vs rewrite/breakpoint/script on desktop) for abuse-prevention and store-policy reasons. requestr can choose differently, but must then own the abuse-prevention story.
6. **The product identity lives in the capture list + inspector + rules, not in the transport.** The transport is commodity plumbing (tun + proxy bridge); the differentiation is column richness, search/filter, protocol decoding, body viewers, replay, and rules.

# (B) Layered architecture blueprint for requestr

Target architecture (seven functional layers plus cross-cutting concerns):

```
L1 Transport          VpnService (tun) | root iptables | Shizuku-assisted | SDK/CDP/Frida tiers
L2 Bridge             native tun2proxy (Rust, pinned 0.8.3)  →  local SOCKS5 (+session-info) → CONNECT listener
L3 MITM/TLS           MitmProxyEngine: ClientHello peek (SNI+ALPN) → per-host leaf (BouncyCastle CA)
                      → JSSE/Conscrypt dual-socket relay → upstream cert sniffing (mitmproxy pattern)
L4 Protocol parsers   HTTP/1.1 (streaming), HTTP/2 (frames+HPACK), WebSocket, SSE, gRPC, DNS, QUIC-passive (QPACK)
L5 Rule engine        gateway (allow/bypass/block/suspend) → mirror → rewrite (replace/modify) → breakpoint
                      → script (JSON bridge) → mock/fixture → throttle → replay (≤255 conn)
L6 Persistence        Room (SQLite, WAL) + FTS5 search + body-files-on-disk + HAR/pcap export
L7 UI                 capture list (Reqable-column-class) + inspector (overview/headers/body/timing/tls/raw) + filters
X  Cross-cutting      pooled buffers, bounded thread pools, Doze/battery, FGS types, notifications, metrics
```

## B.1 Layer 1 — Transport: capturing packets without root

### B.1.1 VpnService (the guaranteed rootless baseline)

The Android contract, per official docs ([developer.android.com/develop/connectivity/vpn](https://developer.android.com/develop/connectivity/vpn), [developer.android.com/reference/android/net/VpnService](https://developer.android.com/reference/android/net/VpnService)):

- `VpnService.prepare(context)` drives the consent dialog; must be re-checked because the user can revoke ("Always-on" revoke removes the app's VPN permission silently).
- `Builder` configuration: `addAddress()` (at least one address, e.g. `10.111.0.2/32` or a documented private pool), `addRoute("0.0.0.0", 0)` and **`addRoute("::", 0)` for IPv6** — a VPN with only IPv4 routes silently misses all IPv6 traffic, which on modern dual-stack networks is a large share of app traffic. `addDnsServer()` (use a **virtual DNS IP inside the VPN pool**, e.g. `198.18.0.1`, and implement DNS in-process — see B.2.4), `setMtu()` (1500 is the safe default on Android; do not exceed the device's network MTU minus overhead or you force fragmentation), `setBlocking(true)` (packet reads block instead of busy-polling; matches how NetBare drives a dedicated reader), `setUnderlyingNetworks()` (API 29+, lets the system optimize and keeps connectivity state honest), and `addAllowedApplication()` / `addDisallowedApplication()` — **exactly one of the two modes**, they are mutually exclusive ([developer.android.com/develop/connectivity/vpn](https://developer.android.com/develop/connectivity/vpn)).
- `establish()` returns a `ParcelFileDescriptor`; platform semantics: **a `read()` on the fd yields one outgoing IP packet; a `write()` injects one incoming IP packet**. The fd is a Linux tun device; the app retains it, typically duplicated into native code (requestr's bridge does this: the Rust `tun2proxy` bridge receives the fd and owns the read/write loop).
- **Loop avoidance is mandatory:** any socket the app itself opens to the outside (upstream legs of the MITM, DNS to real resolvers, report server, collaboration) must be `protect()`ed so it bypasses the tunnel — the classic failure is a "circular connection" where the proxy's own upstream traffic re-enters the tun ([developer.android.com/develop/connectivity/vpn](https://developer.android.com/develop/connectivity/vpn)).
- **Per-app filtering at the transport**: the `addAllowed/DisallowedApplication` API enforces "this app's sockets either do or don't enter the tun" at the kernel level. This is what Reqable's "target application" list exercises (FAQ: "All target applications have been removed", "Applications support bypass mode" v2.25.1) ([reqable.com/en-US/docs/faq/android](https://reqable.com/en-US/docs/faq/android)).

### B.1.2 Why a local VPN cannot capture on some emulators/containers (and the fix)

Covered in depth in D.3, but the invariants: (1) `VpnService.Builder.establish()` needs a working kernel tun device (`/dev/net/tun`, `CONFIG_TUN`); (2) even with tun, the emulator's userspace network path (QEMU SLIRP by default) must route the guest's packets into the tun and back — several system images/kernel builds historically don't, and there are API-30+ reports of tun interfaces that stop delivering packets on emulators (see D.3). Empirically: **validate on physical devices; use proxy-mode (LAYER-2 alternative) inside emulators; use userdebug/rooted images or Redroid-with-proper-tun for CI** (details + docker flags in D.3).

### B.1.3 Root / Shizuku transports (the capability ladder)

- **Root iptables transparent mode** mirrors mitmproxy's transparent design: `iptables -t nat -A OUTPUT -p tcp -m owner ! --uid-owner <own-uid> -j REDIRECT --to-port <proxy-port>` (or nftables dnat), plus recovering the original destination via `SO_ORIGINAL_DST` on the accepted socket ([docs.mitmproxy.org/stable/concepts/modes](https://docs.mitmproxy.org/stable/concepts/modes/)). requestr already has `RootIptablesEngine` + `ProcNetUidResolver`; the correct per-app refinement is `-m owner --uid-owner <target-uid>` ranges. UDP TPROXY for QUIC belongs here only as research (see D.1).
- **Shizuku** grants adb/shell-tier privileges (UID 2000) — useful for scripted system configuration (e.g., `settings`, `cmd connectivity` tweaks, CA-related shell operations, `pm` grants), **not** for data-plane injection into other apps. Keep the current framing: Shizuku = control-plane elevation, never the capture data path ([github.com/RikkaApps/Shizuku](https://github.com/RikkaApps/Shizuku)).
- **Frida tier**: on rooted devices or repackaged (debuggable) apps, Frida gadget/spawn injection can (a) hook TLS pinning, (b) capture SSL keys passively, (c) in HTTP Toolkit-style, intercept the app's HTTP stack directly ([httptoolkit.com/blog/frida-certificate-pinning](https://httptoolkit.com/blog/frida-certificate-pinning/), [github.com/httptoolkit/frida-interception-and-unpinning](https://github.com/httptoolkit/frida-interception-and-unpinning), [frida.re](https://frida.re/)). requestr's `FridaCaptureEngine` fills this rung.
- **SDK tier (own apps)**: the `sdk/` module + OkHttp interceptor + Cronet listener + WebView bridge is the "capture what your own app does" path and is orthogonal to VPN (it is what enables requestr-in-your-own-app without any tunnel).
- **eBPF**: not a shipping layer today. Android kernels ≥5.x can run eBPF but no mainstream interceptor ships an eBPF data path; the realistic uses are uprobes for key extraction. Treat as research-only; do not schedule it.

## B.2 Layer 2 — TUN → proxy bridge

### B.2.1 The decision requestr already made (keep it, harden it)

requestr pins **tun2proxy 0.8.3** in a Rust cdylib bridge (`native/tun2proxy-bridge`, JNI via `jni = 0.21`, tokio 1.53) that takes the VpnService fd and forwards the tunnel through a local SOCKS5 into `MitmProxyEngine`'s CONNECT listener ([github.com/tun2proxy/tun2proxy](https://github.com/tun2proxy/tun2proxy)). This is a sound choice, for reasons validated by this research:

- **The bridge's job is narrow:** convert tun IP packets into local-proxy streams, preserving the original destination (SOCKS5 CONNECT carries host:port) and handling UDP policy (see B.2.4). It is *not* a TCP stack: no userspace TCP reassembly is needed for MITM because the local proxy is a real TCP listener — exactly how Reqable's enhanced mode behaves ("the proxy protocol uses socks5 instead of http", per changelog) and structurally identical to NetBare's `TcpProxyServer` (NIO listener on the VPN subnet) ([reqable.com/en-US/docs/changelogs/android](https://reqable.com/en-US/docs/changelogs/android/), [github.com/MegatronKing/NetBare-Android](https://github.com/MegatronKing/NetBare-Android)).
- tun2proxy features that map 1:1 to needs: HTTP/SOCKS4/4a/5 proxies with auth; **virtual DNS** (SOCKS4a/SOCKS5h-style remote resolution), **DNS over TCP**, **SOCKS5 UDP** with a **UDP gateway (udpgw, UDP-over-TCP)** mode; IPv4+IPv6; and — for per-app attribution — **session-info embedding** (append `+info` to the SOCKS5 username so the local proxy receives `user|tcp|src_ip|src_port`, letting the proxy call `ConnectivityManager.getConnectionOwnerUid(protocol, local, remote)` (API 29+) to resolve the app UID) ([github.com/tun2proxy/tun2proxy](https://github.com/tun2proxy/tun2proxy), [developer.android.com/reference/android/net/ConnectivityManager](https://developer.android.com/reference/android/net/ConnectivityManager)).

### B.2.2 Alternatives considered (and when requestr would switch)

- **gVisor netstack (`gvisor.dev/docs/architecture_guide/networking/`)** — full userspace TCP/IP in Go; what `xjasonlyu/tun2socks` (SOCKS5/HTTP/SS upstream) and sing-box's tun mode use ([github.com/xjasonlyu/tun2socks](https://github.com/xjasonlyu/tun2socks), [gvisor.dev/docs/architecture_guide/networking](https://gvisor.dev/docs/architecture_guide/networking/)). Justified when the goal is **packet-level capture with UDP/QUIC visibility inside the TUN** (the bridge must terminate TCP itself to reassemble flows) — e.g., PCAPdroid-class capture, or requestr's passive QUIC ingestion path. Cost: a Go runtime + an order of magnitude more native code, and gVisor's userspace TCP throughput is below kernel TCP (fine for inspection, wrong default for MITM relay). **Verdict: adopt gVisor only when the product wants on-device packet traces (PCAP export with QUIC), not for MITM.**
- **hev-socks5-tunnel** — C + lwIP, cooperative/coroutine-style I/O, claims the highest throughput/lowest CPU of the tun2socks family, dual-stack, Fullcone UDP, MTU 9000 multi-queue tun, ships an Android VPN reference implementation (`heiher/sockstun`) ([github.com/heiher/hev-socks5-tunnel](https://github.com/heiher/hev-socks5-tunnel), [hev.cc/posts/2023/high-performance-tun2socks](https://hev.cc/posts/2023/high-performance-tun2socks/), [github.com/heiher/sockstun](https://github.com/heiher/sockstun)). Attractive if data-plane throughput becomes the bottleneck (5G, large downloads through the MITM relay); the tradeoff is a second native component with its own build/JNI surface.
- **NetBare-style hand-rolled Java NIO proxy** (parse IP/TCP headers, reassemble, forward to a local listener) — historically proven (HTTP Canary) but it duplicates TCP state-machine work that the platform kernel already does correctly, and modern Android restricts the `/proc/net/tcp` UID dumps NetBare relied on (see B.2.3). Not a direction for a rewrite; keep only as a last-resort fallback on devices where the Rust bridge cannot load (ABI issues).
- **Single-process Netty-only design** (no native bridge): run the proxy as a `ServerSocketChannel` bound to a VPN-subnet address and let the kernel route TUN packets to it (NetBare model). Viable, but it forces the app to implement IPv6 routing, UDP policy, and DNS inside the JVM and bloats the reliability surface; the native bridge handles these cheaply today.

### B.2.3 Per-app UID attribution (three mechanisms, in order of preference)

1. **`ConnectivityManager.getConnectionOwnerUid(protocol, localAddr, remoteAddr)` (API 29+)** — the sanctioned platform API for VPN apps: the local proxy's accepted socket has the tunneled source IP:port, and this call returns the owning UID ([developer.android.com/reference/android/net/ConnectivityManager](https://developer.android.com/reference/android/net/ConnectivityManager)). Pair with tun2proxy `+info` session-embedding so the MITM layer knows the tunneled 5-tuple ([github.com/tun2proxy/tun2proxy](https://github.com/tun2proxy/tun2proxy)). This is the modern replacement for NetBare's `/proc` dumper, which is exactly why NetBare documented `dumpUid` as battery-draining and restricted.
2. **`/proc/net/tcp|udp|tcp6|udp6` parsing** (NetBare `UidDumper`): works on older Android but visibility is restricted on modern releases; treat as legacy fallback only, never the primary path.
3. **Transport-level allowlist** (`addAllowedApplication`, kernel-enforced): gives the *filter*, not the *label*; combine with (1) for per-app columns in the capture list.

### B.2.4 UDP policy — the QUIC gate and DNS

- **DNS:** point `addDnsServer()` at a virtual address inside the tunnel's subnet and implement a DNS proxy in-process (requestr has `dns/DnsParser.kt` + `DohDotDetector.kt`): answer or forward DNS via a `protect()`ed UDP socket (tun2proxy's `--dns` strategies: `virtual` / `over-tcp` / `direct`). Detect and flag DoH/DoT/DoQ (encrypted DNS bypasses the tunnel because it rides 443/853/443-UDP inside the app's own TLS/QUIC — you can only *observe* it, not rewrite it without app cooperation).
- **QUIC gate:** to make HTTP/3 traffic inspectable, the standard product move is to **not forward UDP/443 through the bridge** — Reqable's changelog: "SOCKS5 UDP proxy automatically blocks HTTP3/QUIC requests" ([reqable.com/en-US/docs/changelogs/android](https://reqable.com/en-US/docs/changelogs/android/)). Because HTTP/3 can't be MITM'd with a user CA on Chromium stacks (D.1), the engineering default is: forward UDP only for (a) DNS, (b) apps on an explicit allowlist; drop UDP/443 otherwise, and surface a per-host "QUIC blocked → fell back to HTTP/2" diagnostic (the repo's `http3-row-indicators` design already anticipates this honesty).
- **Passive QUIC observation** (requestr differentiator): keep the existing `quic/` packet path (CID table, RFC 9001 crypto, QPACK decoder) fed from the TUN's UDP packets *before* the bridge drops them — i.e., the bridge should *tee* UDP to both the passive decoder and the drop/forward policy. This is exactly the "honest state" architecture: passive decode when keys are provably available (SDK keylog, Frida keys or app-controlled), QUIC-block + fallback otherwise.

## B.3 Layer 3 — MITM / TLS interception engine

### B.3.1 Certificate authority and leaf generation (the NetBare/BouncyCastle pattern, hardened)

- **CA:** generate a fresh RSA-2048/3072 self-signed CA per install (`CertificateAuthority.kt` already exists); persist the key in the app's AndroidKeyStore-encrypted storage. Root CA properties that matter in practice: `basicConstraints=CA:true` (critical), `keyCertSign`, `digitalSignature`, `crlSign`; the QuicMitm paper notes Android's BoringSSL X.509 parser rejects some CA layouts ("set X509v3 Basic Constraints to empty rather than critical", validity ≤ 3 months to avoid parser quirks) — a checklist to validate against requestr's CA ([madweb.work/papers/2026/madweb26-paper24.pdf](https://madweb.work/papers/2026/madweb26-paper24.pdf)).
- **Per-host leaf certificates:** on each CONNECT, read the hostname (CONNECT authority, or SNI, or upstream-cert sniffing — see below), then issue a leaf with `CN=hostname`, `SANs=[hostname (+ any SANs cloned from the upstream leaf)]`, random **positive** serial with per-CA uniqueness reserve (NetBare's `randomSerial` with a 16-bit increment reserve exists specifically because duplicate/negative serials break browser and client caches), 1-day validity (NetBare) or 3-month window (QuicMitm); return cached leaves for repeat hosts (`ExpiringLruCertCache.kt` already addresses this) ([github.com/MegatronKing/NetBare-Android/blob/master/netbare-core/src/main/java/com/github/megatronking/netbare/ssl/CertificateGenerator.java](https://github.com/MegatronKing/NetBare-Android/blob/master/netbare-core/src/main/java/com/github/megatronking/netbare/ssl/CertificateGenerator.java)).
- **Fingerprint cloning for pinning workarounds:** mitmproxy's trick — sniff the upstream certificate, clone CN + all SANs into the forged leaf; Reqable's documented alternative is a **custom server certificate per domain** (import p12/pem) for pinned hosts ([docs.mitmproxy.org/stable/concepts/how-mitmproxy-works](https://docs.mitmproxy.org/stable/concepts/how-mitmproxy-works/), [reqable.com/en-US/docs/capture/ssl](https://reqable.com/en-US/docs/capture/ssl)).
- **TLS stack:** JSSE with the platform provider — **Conscrypt (BoringSSL)** on Android ([github.com/google/conscrypt](https://github.com/google/conscrypt)). Keep requestr's `sslContextProvider` + `ClientHelloCapture` seam: JSSE's `X509ExtendedKeyManager` receives neither SNI nor ALPN reliably, so the engine must **peek the ClientHello record off the socket first** (parse SNI + ALPN + JA3-ish fingerprint), then hand the identical bytes to the SSLEngine/SSLSocket — requestr's existing `tls/ClientHelloCapture.kt` implements exactly this, and it is the correct senior-engineer pattern (mitmproxy does the same pause-at-SNI trick at the protocol level). Honor **SNI-based leaf selection** and **ALPN** (`h2` vs `http/1.1`) from the peeked data, and enforce TLS 1.2+ (drop SSLv3/TLS1.0/1.1 server-side by default). For tests on the JVM, keep the `SunJSSE` seam; on device, never mix providers per-connection (one SSLContext per direction per connection, pooled).
- **mTLS:** support client certificates on the upstream leg (Reqable documents this for "two-way authentication" scenarios) — an optional `KeyManager` feeding the app-provided client cert, per-domain ([reqable.com/en-US/docs/capture/ssl](https://reqable.com/en-US/docs/capture/ssl)).

### B.3.2 The MITM server + relay loop

Current shape (`MitmProxyEngine`): a `ServerSocket` CONNECT/HTTP listener, per-connection coroutine relays on `Dispatchers.IO`, transaction callback → Room. Senior-engineer refinements, in priority order:

1. **Bound the accept + relay pool.** Per-connection `launch(Dispatchers.IO)` is unbounded; Reqable's own documentation numbers the concurrency ceiling for replay at 255 connections and describes a **thread pool limit for breakpoints** ("each breakpoint request is in a separate thread. If there are too many requests and it exceeds the thread pool limit... it will need to wait") ([reqable.com/en-US/docs/capture/repeat](https://reqable.com/en-US/docs/capture/repeat), [reqable.com/en-US/docs/capture/breakpoint](https://reqable.com/en-US/docs/capture/breakpoint)). Introduce: a bounded dispatcher (e.g., 32–64 relay tasks), a per-connection state machine (not one monitor per socket), and backpressure on `onDecryptedTransaction` (the Room write path must never block relays).
2. **Two-phase write discipline.** Downstream (client) writes must be serialized per connection (requestr already has `clientWriteLock`); upstream writes are the pacing point — respect upstream TCP backpressure with bounded send buffers instead of unbounded `ByteArray`s.
3. **Large-body policy.** Decide at header completion: bodies ≤ threshold (e.g., 1–2 MB) stream into pooled memory buffers and then Room; larger bodies stream to disk (`filesDir/captures/<session>/<id>.<req|res>.bin`) with only metadata + first-N-KB + hash stored in the DB. Reqable renders large payloads as `<...>` in the raw tab precisely to avoid loading them ("Large data is displayed as `<...>` in the raw tab to avoid performance issues") ([reqable.com/en-US/docs/changelogs/android](https://reqable.com/en-US/docs/changelogs/android/)).
4. **Protocol auto-detection on the client leg.** Peeked bytes must disambiguate: TLS ClientHello (→ MITM with leaf by SNI), plaintext proxy request (`GET http://...`/`POST /`), CONNECT, SOCKS5 greeting (Reqable's proxy server auto-detects HTTP vs Socks on one port; requestr's listener may receive raw HTTP or SOCKS5 depending on bridge config — the repo's `ProtocolDetector.kt` covers this, keep it in the hot path before any TLS work).
5. **Upstream certificate sniffing** as a fallback for IP-address CONNECTs (`CONNECT 1.2.3.4:443` with no SNI): pause the client handshake, complete the upstream TLS handshake first, then forge from the real cert ([docs.mitmproxy.org/stable/concepts/how-mitmproxy-works](https://docs.mitmproxy.org/stable/concepts/how-mitmproxy-works/)). This is worth scheduling: it is the difference between "works for 95% of apps" and "works for browsers, CDN edges and IP-pinned clients".

### B.3.3 Getting the CA trusted (the full ladder, in order of power)

1. **User certificate store (rootless):** the `ACTION_ADD_CREDENTIALS` / KeyChain install flow (`CertificateInstallActivity`, already in NetBare) puts the CA in the user store. Since Android 7 (API 24), **apps must opt in** to user CAs via `network-security-config` (`<certificates src="user"/>`); without that, only apps that explicitly trust user CAs (or debug builds of your own apps) will accept the leaf ([developer.android.com/privacy-and-security/security-config](https://developer.android.com/privacy-and-security/security-config), [github.com/MegatronKing/NetBare-Android](https://github.com/MegatronKing/NetBare-Android)). Browser polarity: Chrome's handling has flipped across versions (Reqable FAQ: newer Chrome wants the *user* store, older wanted *system*; try both) ([reqable.com/en-US/docs/faq/android](https://reqable.com/en-US/docs/faq/android)); Firefox Android needs `Use third party CA certificates` secret setting.
2. **System store via root/Magisk:** mount the CA into the system trust store (`/system/etc/security/cacerts` on ≤13; on **Android 14+ the store moved into the `com.android.conscrypt` APEX**, so direct modification needs an APEX-aware Magisk module, and one research setup additionally froze APEX updates with `chattr +i /data/apex/active`) ([httptoolkit.com/blog/android-14-breaks-system-certificate-installation](https://httptoolkit.com/blog/android-14-breaks-system-certificate-installation), [www.g1a55er.net/Android-14-Still-Allows-Modification-of-System-Certificates](https://www.g1a55er.net/Android-14-Still-Allows-Modification-of-System-Certificates), [madweb.work/papers/2026/madweb26-paper24.pdf](https://madweb.work/papers/2026/madweb26-paper24.pdf)). System-store trust maximizes coverage (any app, no per-app opt-in) — this is the QuicMitm path and the QuicMitm paper's CA validity guidance (≤3 months) came from exactly this integration.
3. **Pinning bypass (see D.2):** Frida assertion-style unpinning scripts, objection `android sslpinning disable`, Xposed/LSPosed modules (JustTrustMe/TrustMeAlready), or VirtualApp-style containers — with the honest caveat that native pinning + integrity checks defeat naive hooks ([mas.owasp.org/MASTG/techniques/android/MASTG-TECH-0012](https://mas.owasp.org/MASTG/techniques/android/MASTG-TECH-0012), [github.com/sensepost/objection](https://github.com/sensepost/objection), [github.com/httptoolkit/frida-interception-and-unpinning](https://github.com/httptoolkit/frida-interception-and-unpinning)).
4. **Trust gate:** requestr's `CaTrustGate` ("only FORCE_MITM when the CA is actually trusted client-side") is the right kind of honesty layer — mirror it at the product level: when a handshake fails with `CERTIFICATE_UNKNOWN`/unknown-CA, label the row with the actionable reason (CA missing / pinned / mTLS required) instead of a generic failure (the repo's `tls-failed-detail-*` designs already encode this).

## B.4 Layer 4 — HTTP protocol parsing (the layer where "Reqable-class" is won or lost)

### B.4.1 HTTP/1.1

- Streaming parser over the decrypted socket: request-line, headers (obs-fold handling), body by `Content-Length` or `chunked` (with `Transfer-Encoding` trailers), keep-alive and connection-level reuse, `Expect: 100-continue`, pipelining (Android clients rarely pipeline; tolerate, don't optimize).
- Parse targets per request-record: method, URL, headers (ordered), cookies (parse/serialize), body with Content-Encoding-aware decode (gzip/br/zstd/deflate — `HttpBodyDecoder.kt` exists), and the five timing points (request start/end, response start/end + DNS/connect/TLS split if captured).
- Trailer support: mitmproxy explicitly lists "trailers not supported with HTTP/1.x" as a known limitation ([docs.mitmproxy.org/stable/concepts/protocols](https://docs.mitmproxy.org/stable/concepts/protocols/)) — requestr can do better, but it is a long tail; schedule after h1/h2 parity.
- Content-Length recomputation on any rule-based mutation (Reqable documents this twice, once for rewrite request headers and once for response) ([reqable.com/en-US/docs/capture/rewrite](https://reqable.com/en-US/docs/capture/rewrite)).

### B.4.2 HTTP/2 (the critical upgrade path)

- Client-facing leg: the client negotiates `h2` via ALPN (Conscrypt handles ALPN; the peeked ALPN decides), then speaks **binary frames**: the `PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n` preface, HEADERS/DATA/SETTINGS/PRIORITY/RST_STREAM/PUSH_PROMISE/PING/GOAWAY/WINDOW_UPDATE/CONTINUATION, odd client stream IDs, HPACK header blocks with per-direction dynamic tables, and WINDOW_UPDATE flow control.
- requestr already has a hand-written `Http2Parser`/`Http2Session`/`HpackHuffman`/HPACK decoder with gRPC body reassembly — the same bet NetBare made (its `http2/` package hand-rolled HPACK + Huffman) ([github.com/MegatronKing/NetBare-Android](https://github.com/MegatronKing/NetBare-Android)). Decision point for the plan:
  - Option A (recommended): **adopt Netty's `codec-http2`** for the client-facing h2 server role ([netty.io](https://netty.io/), [github.com/netty/netty](https://github.com/netty/netty)) — it is the most battle-tested JVM HPACK/frame implementation (used by Play, Finagle, gRPC-Java), brings pooled `ByteBuf`s on its event loop, and removes an entire class of parser-security risk. Cost: ~2–4 MB of DEX + strict event-loop threading.

  Hmm — realistic calibration: requestr's `Http2Session` is already wired into `MitmProxyEngine`'s relay loops, already production-shaped, and Netty's `Http2FrameCodec` wants to own the I/O threading model. The plan's honest recommendation: **keep the in-house codec for the client leg only if it passes a fuzz-security budget; otherwise swap the leg to Netty's h2 codec while keeping requestr's session/transaction model** by translating codec events → `H2Frame` (current type) so the UI/persistence layer doesn't change. Either way, the *upstream* leg stays OkHttp for concurrency reasons (B.4.5).
  - HPACK verification: whatever path, run conformance tests against nghttp2's test vectors and the RFC 7541 Python reference — HPACK dynamic-table state is the #1 source of silent misparse bugs (the repo's `HpackHuffman` comment already documents one such QPACK/HPACK crossover bug — evidence the class has earned this testing).
- **HTTP/2 ↔ HTTP/1 translation** is table stakes: when upstream is h2-incompatible, translate (mitmproxy does this via hyper-h2; Reqable's size columns literally document computing h2 headers as if HTTP/1 for display) ([docs.mitmproxy.org/stable/concepts/protocols](https://docs.mitmproxy.org/stable/concepts/protocols/)). This translation is also how HAR export stays uniform (HAR is h1-shaped).
- Push promises: mitmproxy does not advertise them; requestr should neither advertise nor implement (intercept-and-drop, per RFC 7540 §8.2 constraints) ([docs.mitmproxy.org/stable/concepts/protocols](https://docs.mitmproxy.org/stable/concepts/protocols/)).

### B.4.3 WebSocket (RFC 6455)

- Recognize the `Upgrade: websocket` handshake on h1; parse frames (FIN/RSV/opcode, masking — clients MUST mask, servers MUST unmask; fragmentation with CONTINUATION; control frames ping/pong/close), relay bidirectionally while recording each message.
- Product shape from Reqable: per-connection WebSocket message list (text/binary), send/receive icons, timestamps to the millisecond, a 4-k-char cap per text message for chat-style views, forward/reverse ordering, and a frame-level search (Ctrl+F) ([reqable.com/en-US/docs/changelogs/android](https://reqable.com/en-US/docs/changelogs/android/)). requestr's `WebSocketParser.kt` is the base; add the message-list model + persistence (messages table) in the same phase as the parser upgrade.
- Library note: mitmproxy pairs its h1 stack with `wsproto`; on the JVM, Netty's `WebSocketServerProtocolHandler` is the counterpart; OkHttp's WebSocket is client-oriented (replay/"API Testr" WS mode) — both are legit, choose by leg.

### B.4.4 SSE, gRPC, and misc decoders

- **SSE:** `text/event-stream` framing (`event:`/`data:`/`id:`/`retry:`), streamed events as rows; Reqable's "fully support SSE real-time streaming" landed in v2.30.1 — treat as a first-class protocol, not an h1 corner case ([reqable.com/en-US/docs/changelogs/android](https://reqable.com/en-US/docs/changelogs/android/)). `SseParser.kt` exists.
- **gRPC:** rides HTTP/2; detect `content-type: application/grpc` (+ optional `+proto`), each message = 1-byte compressed flag + 4-byte big-endian length + protobuf payload, trailers carry `grpc-status`; streaming modes (unary/server/client/bidi) map to h2 streams. Decode protobuf with `wire`/`protobuf-kotlin` when a descriptor or reflection is available, else hex/raw fallback. Reqable has announced gRPC/Protobuf for v3.2 — requestr's `Http2Session.onDataFrame` already reassembles gRPC bodies; the missing piece is the message framing + status/trailer extraction + UI tab ([reqable.com/en-US/blog](https://reqable.com/en-US/blog)).
- **Body preview matrix:** JSON prettify (with fast tokenizer — Reqable shipped "greatly improve the performance of JSON syntax highlighting" as a changelog item), XML/HTML/JS/CSS, image/audio/video thumbnails by content-type, form-urlencoded, protobuf icon states — the icon taxonomy is directly copyable from Reqable's column docs ([reqable.com/en-US/docs/capture/column](https://reqable.com/en-US/docs/capture/column)).

### B.4.5 Upstream client strategy

- The upstream leg should be a **real HTTP client, not a second raw protocol server**: OkHttp gives connection pooling, h2 frames, WebSocket, redirects, timeouts, `EventListener` for timing, and TLS via the same Conscrypt provider; it also powers the replay/API-Testr path and requestr's own SDK interceptor ([square.github.io/okhttp](https://square.github.io/okhttp/)). OkHttp's h2/hpacks are used in production at massive scale — that de-risks the HPACK correctness problem on the upstream side for free.
- OkHttp HTTP/3 status: **not shipped** — OkHttp's `Protocol.HTTP_3` remains an enumeration placeholder and its issue tracker explicitly says QUIC requires a custom interceptor/engine ([github.com/square/okhttp/issues/907](https://github.com/square/okhttp/issues/907)); the only in-JVM h3 option remains Jetty's HTTP/3 server/client (built on quiche via JNI) or a Rust bridge using quiche/quinn ([javadoc.jetty.org/jetty-12/org/eclipse/jetty/http3/qpack/QpackEncoder](https://javadoc.jetty.org/jetty-12/org/eclipse/jetty/http3/qpack/QpackEncoder.html), [github.com/cloudflare/quiche](https://github.com/cloudflare/quiche), [github.com/quinn-rs/quinn](https://github.com/quinn-rs/quinn)). For API-Testr-style *sending* h3 requests, the pragmatic route is **Cronet** (Chromium netstack, first-party H3 client on Android, `enableQuic=true`) — the QuicMitm study found real-world app QUIC overwhelmingly comes from Cronet/WebView anyway ([madweb.work/papers/2026/madweb26-paper24.pdf](https://madweb.work/papers/2026/madweb26-paper24.pdf)).
- TLS key export seam: keep a per-session "keys" recorder (SSLKEYLOGFILE-shaped lines from the SDK keylog + Frida tier) so captured flows can be decrypted offline in Wireshark — this is how the passive QUIC tier stays honest (D.1) ([github.com/saleemrashid/frida-sslkeylog](https://github.com/saleemrashid/frida-sslkeylog)).

### B.4.6 DNS layer (capture-adjacent, high value)

- Parse DNS over the tunnel (UDP 53, TCP 53 fallback), record queries per app (host, type, resolved IPs, latency), detect DoH/DoT/DoQ flows (443/TLS/QUIC to known resolver hosts) and label them (`DohDotDetector.kt` exists). This is the only interception point for "which app resolved what" that still works when MITM is impossible.

## B.5 Layer 5 — Rule engine (Reqable's debug tool taxonomy, rebuilt for mobile)

Design target: one ordered, folder-able rule list (Reqable: "Rules are matched from top to bottom... import and export supported", folder-level management) against a uniform `Flow` object; every flow passes through it in the relay path ([reqable.com/en-US/docs/capture/rewrite](https://reqable.com/en-US/docs/capture/rewrite)). Map the existing requestr classes (`RuleEnforcer`, `RuleTemplateExpander`, `ChaosInjector`, `NetworkConditionInjector`, `MockFixtureLoader`, `ConnectReplay`, `ConnectControl`) onto this taxonomy:

1. **Gateway (L4/L7 traffic control)** — allow-only / bypass / block / suspend on domain, IP/CIDR, HTTP (method/host/header), WebSocket; priority `allow-only > bypass > block > suspend`; blocked traffic optionally shown in list; suspend simulates timeout (Reqable semantics) ([reqable.com/en-US/docs/capture/gateway](https://reqable.com/en-US/docs/capture/gateway)).
2. **Mirror (host mapping at proxy layer)** — map host A → host B for all flows, with explicit Host / SNI / CN policies (preserve | use CONNECT address | use mirror address); applied *before* TLS so the leaf is signed for the right name ([reqable.com/en-US/docs/capture/mirror](https://reqable.com/en-US/docs/capture/mirror)).
3. **Rewrite** — redirection (Map Remote; preserve-host toggle; directory match; max one redirection per request), replace-request, replace-response (status/headers/body from empty/text/file), modify-request/modify-response (delete/replace header, query params, regex with `$group` capture references); **Content-Length always recomputed**; execution order redirection → replacement → modification ([reqable.com/en-US/docs/capture/rewrite](https://reqable.com/en-US/docs/capture/rewrite)).
4. **Breakpoint** — wildcard URL rules; on hit, pause the flow, present the editable request/response to the UI, resume/replace/abort; per-hit thread from a **bounded pool** (Reqable documents the pool ceiling: "exceeds the thread pool limit... wait until existing breakpoint requests are completed"), and invalidation on client/server disconnect ([reqable.com/en-US/docs/capture/breakpoint](https://reqable.com/en-US/docs/capture/breakpoint)). Mobile note: Reqable gated this to desktop "to prevent abuse"; requestr may ship it, but it requires foreground-service + notification survivability and a strict timeout policy (a stalled breakpoint must not wedge the relay for other flows — bound by the pool, not by luck).
5. **Script** — Reqable's model: `onRequest(context, request)` / `onResponse(context, response)` in Python3, returning the mutated request, `None` to abort, and a `context.shared` channel between the two invocations (which run in different processes) ([reqable.com/en-US/docs/capture/script](https://reqable.com/en-US/docs/capture/script)). On Android, embedding Python3 is heavy (Chaquo or a Lua/JS alternative); the architecture-level constraint is that the script engine is *out-of-process and JSON-serialized* — the capture core hands a JSOn-serialized request, gets back a modified one. requestr's plan: implement the same contract with a small embedded scripting runtime (e.g., QuickJS via jni or Chaquopy) in a later phase; the interface (request/response JSON + kill-switch) is what matters now.
6. **Mock / fixture** — serve canned responses for matched flows (Reqable replace/script overlap; requestr already has `MockFixtureLoader`).
7. **Network throttling** — Reqable's presets table (offline/bad/slow/fast/2G/3G/4G/5G/wi-fi with bandwidth ranges, latency floors, loss rates) is a ready-made spec; implement as a token-bucket + delay + drop shaper in the relay path ([reqable.com/en-US/docs/capture/network-condition](https://reqable.com/en-US/docs/capture/network-condition)).
8. **Repeat/replay** — send captured flows N times with delay/interval and proxy choice, concurrency cap 255, results feed back into the capture list when proxied through the debug engine ([reqable.com/en-US/docs/capture/repeat](https://reqable.com/en-US/docs/capture/repeat)); requestr's `ConnectReplay` is the base.
9. **Request/response diffing** — Reqable ships a diff view (capture vs replayed, or two flows); cheap to add once the transaction model is stable ([reqable.com/en-US/docs/capture/diff](https://reqable.com/en-US/docs/capture/diff)).

Per-flow, expose which rules touched it (Reqable's "interceptor" column icons: mirror/rewrite/breakpoint/script) — this is both great UX and a debugging aid for the rule engine itself ([reqable.com/en-US/docs/capture/column](https://reqable.com/en-US/docs/capture/column)).

## B.6 Layer 6 — Persistence, search, export

- **Room + SQLite (WAL).** Current repo already persists `CapturedTrafficEntity`/`CaptureSessionEntity`. Senior refinements: (a) normalized tables for headers/timing/websocket-messages/TLS-info keyed by transaction id; (b) **body spill policy** — bodies under N bytes inline (BLOB), larger bodies as files + metadata (B.3.2.3); (c) a **write queue** on a dedicated dispatcher so relay threads never block on IO; (d) session-scoped pruning (age + size caps).

Add body-text extraction only for text content-types (bounded size); binary bodies indexed by filename/hash only.
- **Export formats:**
  - **HAR 1.2** ([github.com/ahmadnassri/har-spec](https://github.com/ahmadnassri/har-spec)): per-entry request/response (headers, cookies, postData, content{size,mimeType,text,encoding}, timings{dns,connect,ssl,send,wait,receive}); import AND export; base64-encode binary content. ## B.8 Cross-cutting: performance, threading, memory, battery, notifications

### B.8.1 Threading and event model (the one decision that sets the ceiling)

- Transport loop: the fd read/write loop is owned by native (tun2proxy tokio) — correct per architecture. Kotlin side handles: bridge↔proxy connectivity (SOCKS5/CONNECT handshake), one **bounded** relay dispatcher for MITM connections, and a **single-writer** persistence queue.
- Per-connection model: prefer **few threads + async I/O** (reuse the coroutines already in place, but bound concurrency and never `runBlocking` in relays); NetBare's single-threaded `Selector` demonstrated this works for a whole device; Netty's event-loop model is the JVM gold standard if the h2 leg moves to Netty ([netty.io](https://netty.io/)).
- Per-request visibility: Reqable "Each breakpoint request is in a separate thread... thread pool limit" — the same bounded-pool idea applies to breakpoints and scripting callbacks ([reqable.com/en-US/docs/capture/breakpoint](https://reqable.com/en-US/docs/capture/breakpoint)).
- Zero-copy principles: pass `ByteBuffer`s/`ByteBuf`s down the pipeline (NetBare's interceptor signature is literally `intercept(chain, ByteBuffer)`); avoid String-converting large bodies; pool buffers in the hot path (the repo's `PacketPump` already does this at the tun boundary — extend the discipline to relay buffers).

### B.8.2 Memory caps

- Tun read buffer = MTU + IP/UDP headroom, pooled ring; per-flow buffers capped (e.g., 512 KB–2 MB); bodies beyond cap spill to disk immediately (B.3.2.3); QUIC passive tables (CID → connection state) bounded by LRU eviction (repo `QuicCidTable`); capture list capped by session limits with oldest-first pruning — reference: Reqable's own perf items (memory reduction, raw-tab `<...>` truncation, JSON highlighting speedups) show where the real-world costs are ([reqable.com/en-US/docs/changelogs/android](https://reqable.com/en-US/docs/changelogs/android/)).

### B.8.3 Battery / Doze / foreground service

- The VPN service must be a **foreground service** with a persistent notification (Reqable's NetBare lineage hard-requires the notification: "强制要求在通知栏提示用户服务正在运行"); on Android 14+ declare `foregroundServiceType="dataSync"` — **VPN apps are an explicitly allowed dataSync exception**, and required permission is `FOREGROUND_SERVICE_DATA_SYNC`; be aware of the 6-hour/day dataSync timeout on API 34+ (Android 15 adds `onTimeout`) ([developer.android.com/about/versions/14/changes/fgs-types-required](https://developer.android.com/about/versions/14/changes/fgs-types-required), [developer.android.com/develop/background-work/services/fgs/service-types](https://developer.android.com/develop/background-work/services/fgs/service-types), [developer.android.com/develop/background-work/services/fgs/timeout](https://developer.android.com/develop/background-work/services/fgs/timeout)).
- Android 13+ needs `POST_NOTIFICATIONS` runtime permission for the capture notification; Android 12+ restricts FGS launches from background — start capture only from visible UI; keep the service `START_STICKY` and re-arm on `onRevoke()` (always-on revoke) ([developer.android.com/develop/connectivity/vpn](https://developer.android.com/develop/connectivity/vpn)).
- Doze: hold a partial wake lock while actively relaying (the repo's `RequestrVpnService` already does); `requestIgnoreBatteryOptimizations` is Play-sensitive — gate it behind an explicit user setting with honest copy.
- Per-app bypass / allowlist must be re-applied on service restart, and the Builder is re-established on every network change (`onNetworkChanged`) — a classic source of "VPN connected but no traffic after Wi-Fi→mobile switch".

### B.8.4 Metrics

- Keep per-transaction counters (bytes, duration) already persisted; add per-engine health probes (repo has `CaptureMethodWatcher`) and a feed into the capture row model (Reqable's "device" + "application" columns are the visible tip; the hidden requirement is a stable flow→app→device attribution pipeline, B.2.3).

## Phase 0 — Baseline hardening of the existing capture path (2–3 sprints)

Goals: make the current VPN→bridge→MITM path correct, bounded, and restart-safe before adding surface.

- **Transport:** dual-stack VPN (add `::/0` route + IPv6 DNS); `setUnderlyingNetworks`; Builder re-establish on network change; `onRevoke` handling; per-app allow/disallow persistence across restarts; tun read-loop packet counters for the health watcher.

# (D) Open problems and risks

## D.1 HTTP/3 / QUIC — the hard part, stated precisely

**Why it is hard (three independent walls):**

1. **Transport:** QUIC is UDP; the MITM relay path is TCP-shaped. CONNECT proxies cannot carry it — mitmproxy's own docs: "HTTP/3 support in proxy mode is not generally useful, because the proxy protocol (HTTP CONNECT) is TCP-only" ([docs.mitmproxy.org/stable/concepts/protocols](https://docs.mitmproxy.org/stable/concepts/protocols/)). You need a UDP data path into the MITM engine: tun UDP packets → in-process QUIC server endpoint.
2. **TLS/cert trust:** QuicMitm demonstrates full QUIC MITM is *possible* (quinn + rustls dynamic certs + stream-demux; captured TCP:443 and UDP:443 via root iptables; tested on 3,452 Android apps) ([madweb.work/papers/2026/madweb26-paper24.pdf](https://madweb.work/papers/2026/madweb26-paper24.pdf)). But the client must trust the CA — and **Chromium won't** for QUIC: "Chrome will not trust a user-added CA for QUIC connections"; the documented workaround is to block QUIC or use `--ignore-certificate-errors-spki-list` ([chromium.org/quic/playing-with-quic](https://www.chromium.org/quic/playing-with-quic/)). Since the QuicMitm study found real-world QUIC on Android is **overwhelmingly Chromium**: ~49% of 3,452 apps generated HTTP/3 traffic, almost all to Google destinations, via Cronet/Play services/WebView/ad SDKs ([madweb.work/papers/2026/madweb26-paper24.pdf](https://madweb.work/papers/2026/madweb26-paper24.pdf)) — a user-CA-based on-device QUIC MITM would decrypt almost nothing of value on modern devices. (Root-level system CA doesn't fix this: it is a **Chromium policy**, not a store lookup.) Certificate Transparency on Google-controlled hostnames adds another refusal layer for Chrome ([httptoolkit.com/blog/chrome-android-certificate-transparency](https://httptoolkit.com/blog/chrome-android-certificate-transparency/)).
3. **Stream semantics:** HTTP/3 multiplexes requests over bidirectional streams with QPACK header blocks on the control stream; a MITM must demux, re-order (buffering whole payloads per stream — the QuicMitm "frame-ordered stream management" trick), and re-map streams 1:1 to the upstream connection — with 1-RTT/0-RTT handshakes and connection migration to contend with ([madweb.work/papers/2026/madweb26-paper24.pdf](https://madweb.work/papers/2026/madweb26-paper24.pdf)).

**How the industry actually handles it (the matrix requestr should copy):**

| Tool | Approach | Ref |
|---|---|---|
| Reqable (capture) | QUIC blocked in the tunnel (SOCKS5 UDP gateway drops HTTP/3); clients fall back to h2; HTTP/3 MITM "not yet supported" | [reqable.com/en-US/docs/introduction](https://reqable.com/en-US/docs/introduction/), [reqable.com/en-US/docs/changelogs/android](https://reqable.com/en-US/docs/changelogs/android/) |
| Reqable (API testing) | H3 as a *sending client* with auto-downgrade | [reqable.com/en-US/docs/rest/protocol](https://reqable.com/en-US/docs/rest/protocol/) |
| mitmproxy 11 | H3 MITM via aioquic in reverse/local/WireGuard modes; QUIC v1 only; cURL-tested; transparent UDP not working | [mitmproxy.org/posts/releases/mitmproxy-11](https://www.mitmproxy.org/posts/releases/mitmproxy-11/), [docs.mitmproxy.org/stable/concepts/protocols](https://docs.mitmproxy.org/stable/concepts/protocols/) |
| QuicMitm (research) | Full QUIC MITM with root + system CA; works for non-Chromium clients; Chromium refuses user CAs for QUIC | [madweb.work/papers/2026/madweb26-paper24.pdf](https://madweb.work/papers/2026/madweb26-paper24.pdf) |
| requestr (current) | Passive QUIC decode from keylog-verified keys + honest undecrypted states; **right architecture, keep** | repo `quic/` module |

**Recommended requestr strategy (defensible, honest, differentiated):**
1. **Block-or-tee, never pretend:** per the Reqable precedent, drop UDP/443 at the bridge by default and badge the fallback; tee packets to the passive QUIC decoder.
2. **Passive decode stays key-first:** only decode when keys are provably available (SDK keylog / Frida session-key hook via BoringSSL `SSL_CTX_set_keylog_callback` or `ssl_log_secret` patterns — the same mechanism Wireshark consumes as an SSLKEYLOGFILE; requestr's `TlsKeyLogRegistry` is the seam) ([github.com/saleemrashid/frida-sslkeylog](https://github.com/saleemrashid/frida-sslkeylog)).
3. **Server-side H3 MITM as an explicit advanced mode:** port the QuicMitm design when a JVM/Rust QUIC server endpoint is warranted — candidates on the menu: quiche (Rust, Cloudflare, battle-tested), quinn+rustls (Rust, tokio; QuicMitm's pick), Jetty's HTTP/3 (Java, includes QPACK encoder/decoder), aioquic (Python — only if the script/coresplit changes), or quic-go (Go, only in a gVisor-style bridge future) ([github.com/cloudflare/quiche](https://github.com/cloudflare/quiche), [github.com/quinn-rs/quinn](https://github.com/quinn-rs/quinn), [javadoc.jetty.org](https://javadoc.jetty.org/jetty-12/org/eclipse/jetty/http3/qpack/QpackEncoder.html), [github.com/aiortc/aioquic](https://github.com/aiortc/aioquic), [quic-go](https://github.com/quic-go/quic-go)). Label the mode's coverage honestly ("works for non-Chromium clients; Chromium apps fall back to h2 automatically"). Note QPACK reference material for the decoder: nghttp3's manual is the canonical walkthrough ([nghttp2.org/nghttp3/qpack-howto.html](https://nghttp2.org/nghttp3/qpack-howto.html)).
4. **Do not depend on OkHttp for H3:** OkHttp lists `Protocol.HTTP_3` without an implementation even in 5.x alphas; use Cronet for the API-Testr H3 client ([github.com/square/okhttp/issues/907](https://github.com/square/okhttp/issues/907)).

## D.2 Certificate trust and pinning — the coverage ceiling

- **User CA coverage is app-opt-in since Android 7:** without `network-security-config` trust-anchors, apps reject user-store CAs ([developer.android.com/privacy-and-security/security-config](https://developer.android.com/privacy-and-security/security-config)). Reqable/Charles/HTTP Canary all document this; Charles is blunt: "SSL Proxying on Android can only be used with applications you control" ([charlesproxy.com/documentation/using-charles/ssl-certificates](https://www.charlesproxy.com/documentation/using-charles/ssl-certificates/)).
- **Pinning bypass tooling is a ladder, not a switch:** runtime hooks (Frida/objection `android sslpinning disable`, universal unpinning scripts), framework hooks (Xposed/LSPosed + JustTrustMe/TrustMeAlready), and containers (VirtualApp-wrapped apps inherit the container's trust config; HTTP Canary's documented third-party-app route) ([mas.owasp.org/MASTG/techniques/android/MASTG-TECH-0012](https://mas.owasp.org/MASTG/techniques/android/MASTG-TECH-0012), [github.com/sensepost/objection](https://github.com/sensepost/objection), [github.com/Fuzion24/JustTrustMe](https://github.com/Fuzion24/JustTrustMe), [github.com/virb3/trustmealready](https://github.com/virb3/trustmealready), [github.com/asLody/VirtualApp](https://github.com/asLody/VirtualApp), [github.com/99969/HttpCanary/blob/master/app_ug_zh.md](https://github.com/99969/HttpCanary/blob/master/app_ug_zh.md)). Native pinning (e.g., NDK builds of OpenSSL/rustls pinning, SPKI pinning in native code) defeats all of the above; anti-Frida/integrity checks (Play Integrity, `ptrace` guards) add friction; server-side pinnending with custom certs (Reqable's documented per-domain server certificate) is the only deterministic escape hatch ([reqable.com/en-US/docs/capture/ssl](https://reqable.com/en-US/docs/capture/ssl)).
- **Android 14 trust-store change:** system cert store moved into the `com.android.conscrypt` APEX; root CA mounting now requires APEX-aware Magisk modules, and APEX updates can silently revert your CA (QuicMitm froze `/data/apex/active` with `chattr +i`) ([httptoolkit.com/blog/android-14-breaks-system-certificate-installation](https://httptoolkit.com/blog/android-14-breaks-system-certificate-installation), [www.g1a55er.net/Android-14-Still-Allows-Modification-of-System-Certificates](https://www.g1a55er.net/Android-14-Still-Allows-Modification-of-System-Certificates), [madweb.work/papers/2026/madweb26-paper24.pdf](https://madweb.work/papers/2026/madweb26-paper24.pdf)).
- **Browser quirks to encode in the first-run flow:** Chrome's user-vs-system store requirement has flipped across versions (Reqable FAQ advises trying both) ([reqable.com/en-US/docs/faq/android](https://reqable.com/en-US/docs/faq/android)); Firefox Android needs its secret "Use third party CA certificates" toggle ([reqable.com/en-US/docs/faq/android](https://reqable.com/en-US/docs/faq/android)); Chromium refuses user CAs for QUIC entirely (D.1).
- **Policy position:** ship the ladder (user CA → system CA via root → Frida tier → container) with per-tier honest labeling (the repo's capture-tier design already lists exactly this ladder), and treat "undecryptable (pinned/mTLS)" as a first-class capture state with actionable remediation steps, never as a silent hole.

## D.3 Emulator / Redroid — why tun VPN capture fails there, and the workarounds

- **The mechanism:** `VpnService.Builder.establish()` requires the device kernel to provide a tun device. The Android Studio emulator runs a QEMU-based virtual machine whose network path is userspace (SLIRP by default; virtio-net with a tap backend on some images), and its goldfish/virtual-device kernels do not uniformly ship a working `CONFIG_TUN` userland contract (`/dev/net/tun` reliably openable + packets actually routed into it). Empirically the failure appears in two flavors: `establish()` throws or the interface never exists (kernel/tun gap), or tun exists but **zero packets arrive** (image/network-stack gap — including API-30+ reports of tun interfaces that stop delivering) ([developer.android.com/studio/run/emulator-networking](https://developer.android.com/studio/run/emulator-networking), [developer.android.com/studio/run/emulator-troubleshooting](https://developer.android.com/studio/run/emulator-troubleshooting), [github.com/SagerNet/sing-box/issues/3701](https://github.com/SagerNet/sing-box/issues/3701), [reddit.com/r/androiddev: VpnService TUN stops receiving packets](https://www.reddit.com/r/androiddev/comments/1sgkx3e/vpnservice_tun_interface_stops_receiving_packets/)).
- **Redroid (Android-in-Docker):** the guest **shares the host kernel**, so the tun contract is the *host's*: the host needs `CONFIG_TUN` (+ `modprobe tun`), `/dev/net/tun` must exist and be passed through, and the container needs `--privileged` or `--cap-add net_admin --cap-add net_raw --cap-add mknod` plus `--device /dev/net/tun`; even then, Android routing inside the container (routes into the VPN table, IPv6 sysctls, host NAT/forwarding) is the usual second failure — see the maintained redroid issue threads for the canonical docker flags ([github.com/remote-android/redroid-doc/issues/635](https://github.com/remote-android/redroid-doc/issues/635), [github.com/remote-android/redroid-doc/issues/765](https://github.com/remote-android/redroid-doc/issues/765)).
- **Workarounds, in order of reliability:**
  1. **Physical device** (primary test target for VPN-tier code; nothing else exercises the real kernel + radio stack).
  2. **Emulator proxy-mode instead of VPN-mode**: point the app under test's (or the emulator's Wi-Fi) proxy at a host-side listener running the same MITM engine — the transport layer differs, the MITM/parser/rule layers are identical. This keeps CI meaningful on devices/emulators without tun.
  3. **userdebug/rooted images**: custom kernel with tun enabled, or a rooted image + the root iptables engine (tier 2) which needs no tun at all.
  4. **Redroid with a tun-enabled host kernel** (docker flags above) for containerized CI; validate the routing path with `ip a`/`ip route` from inside the container before debugging the app ([github.com/remote-android/redroid-doc](https://github.com/remote-android/redroid-doc)).
  5. **Nested virtualized networking** (host-level tap → guest) on QEMU/KVM setups where you control the kernel config — the AOSP Cuttlefish-style route; expensive, only for specialized transport testing.
- **Go/no-go rule for the product:** never block a release on emulator VPN capture; the emulator is for UI/parser/rule tests (proxy mode), the physical device is the transport truth.
